# Repository Guidelines

## 프로젝트 구조 및 구성

이 저장소는 Codex 스킬과 홈페이지 리서치 자료로 구성된다.

- `.agents/skills/homepage-reference-analyzer/`: 프로젝트에서 자동 인식되는 스킬 폴더
- `SKILL.md`: 스킬 실행 조건, 작업 순서, 동작 범위
- `references/`: 입력, 분석, 출력 및 미확정 규칙
- `scripts/`: URL 수집·중복 정리 및 결과 검사 도구
- `agents/openai.yaml`: 사용자에게 표시되는 스킬 정보
- `리서치/`: 원본 리서치 자료. 파일명에 `[리서치 결과]`가 있으면 기본 자료로 사용
- `홈페이지_레퍼런스_분석_스킬_예상내용.txt`: 설계 메모. 확정된 동작과 내용이 일치하도록 관리

분석 과정에서 원본 리서치 파일을 수정하지 않는다. 생성한 목록과 보고서는 출력 폴더가 정해진 후 별도 위치에 저장한다.

## 개발 및 검사 명령어

별도의 빌드 시스템이나 패키지 설정은 없다. Python 3으로 직접 실행한다.

```powershell
python .agents\skills\homepage-reference-analyzer\scripts\collect_references.py .\리서치 --output .\reference-inventory.json
python .agents\skills\homepage-reference-analyzer\scripts\validate_results.py .\results\01_홈페이지별_분석_001-100.txt
python -m py_compile .agents\skills\homepage-reference-analyzer\scripts\*.py
```

스킬 구조는 시스템의 `quick_validate.py`로 검사한다. 이 명령은 현재 Python 환경에 PyYAML이 설치되어 있어야 한다.

## 작성 스타일 및 이름 규칙

Markdown, YAML, TXT, Python 파일은 UTF-8로 저장한다. Python은 공백 4칸 들여쓰기와 타입 힌트를 사용한다. 함수와 변수는 `snake_case`, 상수는 `UPPER_CASE`로 작성한다. 별도로 문서화하지 않은 외부 패키지는 추가하지 않는다.

스킬 폴더는 영문 소문자 kebab-case로 작성한다. `references/` 파일은 내용을 알 수 있는 영문 소문자 이름을 사용한다. `SKILL.md`에는 짧고 명령형인 핵심 절차만 두고, 상세 규칙과 예시는 직접 연결된 참조 파일로 분리한다.

## 가상 클라이언트 생성 및 분석 지침

새로운 클라이언트를 생성하거나 가상 클라이언트 분석 보고서를 작성할 때에는 반드시 **`가상 클라이언트/가상 클라이언트 기반 분석 결과 작성 양식.md`**에 정의된 9단계 분석 프로세스 및 6대 필수 작성 양식 구조를 기반으로 작성한다.

1. **클라이언트 재사용 금지 및 일회성 생성 원칙:**
   - 한 번 생성되거나 사용된 가상 클라이언트는 다시 재사용하지 않는다.
   - 새로운 클라이언트 도출 요청 시 기존 클라이언트(이름, 브랜드명, 요청 내용 등)와 중복되지 않는 신규 클라이언트를 새로 생성하여 작성한다.

2. **9단계 분석 프로세스 적용:**
   - 1) 기본 정보 설정 → 2) 원하는 항목 수집 → 3) 정보 단위 변환(사실/개념/절차/과정) → 4) 분류 및 그룹화 → 5) 계층 구조 작성(메뉴 폭 5~9개, 깊이 5단계 이내) → 6) 레이블링 → 7) 내비게이션 연결 → 8) 와이어프레임 화면 영역 배치 → 9) 대조 및 반복 검토

3. **6대 필수 작성 양식 구조:**
   - `1. 가상 클라이언트` (프로젝트 주제, 제작 목적, 제공 자료, 적용 매체)
   - `2. 클라이언트 요구사항` (요청 항목, 중요도, 관련 자료, 필요한 기능)
   - `3. 정보 구조` (주제, 부주제, 메뉴, 콘텐츠, 정보 유형)
   - `4. 내비게이션` (시작 화면, 이동 경로, 연결 페이지, 검색 및 위치 안내)
   - `5. 화면 구성` (헤더, 내비게이션, 핵심 콘텐츠(바디), 보조 콘텐츠(어사이드), 푸터)
   - `6. 검토 결과` (누락 항목, 중복 항목, 사용자 관점의 개선점, 수정 사항)

4. **스토리보드 및 와이어프레임 다이내믹 레이아웃 차별화 원칙:**
   - 모든 클라이언트에 동일한 상하 세로 나열형(Top Bar - Header - GNB - Hero - 3열 카드 - Aside - Footer) 템플릿 사용을 엄격히 금지한다.
   - 고정된 소수 템플릿에 가두지 않고, `master_references1.txt`, `master_references2.txt`의 100여 개 실존 뷰티 웹사이트 분석 데이터를 **'클라이언트의 비즈니스 문제를 해결하기 위한 검증된 UX 도구'**로 활용하여 **4대 아키텍처 축(내비게이션 쉘, 메인 인터랙션 뷰포트 구도, 제품 쇼케이스, 스토리 & 사후 경험 캔버스)**을 클라이언트의 핵심 미션에 맞춰 매번 새롭게 합성하고 100% 독창적인 DOM/CSS 레이아웃을 생성한다.
   - **[1 Section = 1 Single Core Content 원칙]:** 한 섹션 안에 여러 기능을 억지로 우겨넣지 않고, 스크롤에 따라 1개 섹션당 1개의 핵심 콘텐츠/경험이 화면 전체 뷰포트를 독점하도록 전면 분리한다.
   - **[개별 시안 독립 완결형 풀스펙 규칙]:** 시안 1부터 시안 5까지는 단순 요약본이 아니라, 각각이 독자적인 페르소나, 3-Depth 15~25개 상세 노드 트리, 전략적 장단점(Trade-off)을 갖춘 독립 완성형 기획서로 작성한다.
   - **[사이트맵 최적 병합 5대 평가 매트릭스]:** 5개 완성형 시안의 장단점을 대조하는 평가 매트릭스와 전략적 채택/기각 논리(Rationale)를 명시하고, 최적 병합 파일 상단에만 단일 SVG 차트를 연동한다.
   - **[서비스 흐름도 다차원 분기 및 예외 복구]:** 단순 일직선 나열을 금지하고, 4대 진입 트랙, 5대 조건부 판단 분기({?}), 4대 예외 및 실패 복구 루프(Fallback Loops), 사후 리텐션/바우처 환급 루프를 포함한다.
   - 메인 핵심 영역에 클라이언트 비즈니스에 특화된 실물 제품/키트 쇼케이스(Product Showcase Section)를 독립된 전일 섹션으로 전면 배치한다.

5. **브랜드 정체성 정합성 및 디자인 완성도 (Brand Alignment & Design Perfection) 필수 원칙:**
   - **[브랜드 서사 및 코어 메시지 필수 연계]:** 모든 기획 및 설계 문서는 사단(士團) 브랜드의 핵심 메시지(*"내가 머무는 공간과 시간의 깊이, 나만의 시그니처 향으로 완성하는 어사 비밀 첩보"*) 및 3대 마패 체계(1마패 일상 / 2마패 감성 / 3마패 올데이 / 비밀 첩보 레이어링 랩)와 100% 일치해야 한다.
   - **[하이엔드 아트 디렉션 및 룩앤필 완성도]:** 촌스러운 사극풍/한방 화장품/저가 굿즈 류의 클리셰를 전면 금지하고, 퓨어 화이트(`#FFFFFF`)와 솔리드 블랙(`#000000`), 나눔명조-산세리프의 섬세한 자간/행간 타이포그래피 위계, 능화창(菱花窓) 기하학 실선 프레임 등 이솝·르라보 수준의 감각적인 **네오 코리안 미니멀리즘(Neo-Korean Aesthetic)**을 구현한다.
   - **[3대 디자인 완성도 검증 축]:** 검토 결과(6단계) 및 평가 매트릭스에 1) 브랜드 정체성 일치도(Brand Alignment), 2) 시각적 심미성 및 여백의 완성도(Aesthetic Quality), 3) 디깅/소장 가치(Emotional Engagement)를 필수 지표로 반영한다.

## 시험 지침

현재 자동 시험 프레임워크와 커버리지 기준은 없다. 변경 전후로 Python 문법, `[리서치 결과]` 문자열 인식, 중복 URL, 잘못된 URL, 100개 초과 분할을 확인한다. 시험 결과는 임시 위치에 저장하고 원본 리서치 파일을 덮어쓰지 않는다.

4단계 분류 기준과 5단계 결과 양식은 아직 미확정이다. 두 기준이 정해지기 전에는 전체 분석이 완성됐다고 보고하지 않는다.

## 커밋 및 Pull Request 지침

현재 Git 기록이 없어 기존 커밋 규칙을 확인할 수 없다. 커밋은 `feat:`, `fix:`, `docs:`, `test:` 같은 접두사와 짧은 명령형 설명을 사용한다.

Pull Request에는 변경 목적, 수정한 경로, 대표 입력·출력 예시, 미확정 사항, 실행하지 않은 시험을 기록한다. 리서치 자료를 변경했다면 출처와 변경 이유도 명시한다.
