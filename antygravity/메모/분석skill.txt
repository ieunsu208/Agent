# 사단 UX/UI 레퍼런스 리서치 수행

이 Skill은 단순 사이트 수집이 아닌 "다양한 UX 구조 확보"를 목표로 한다. 유사 결과 반복 시 작업 실패로 간주하며, 목표 수량을 채우기 위한 억지 수집(Quantity Padding)을 절대 금지한다.

## 1. 입력 및 사전 준비

1. 사용자의 `$ARGUMENTS`를 확인하여 리서치 방향성을 설정한다.
2. 수집을 시작하기 전, 기존 결과 파일인 `master_references.txt`를 반드시 읽고 분석한다.
3. 브랜드 컨텍스트(사단: 유일성, 실용성, 스토리텔링 / Oriental Modern 무드)를 리서치 기준으로 설정한다.

## 2. 1차 수집 및 필수 검증 (자동 제외 로직)

리서치 과정에서 다음 조건에 하나라도 해당하면 신규 후보에서 즉시 제외한다.

*   **링크 유효성:** HTTP 상태 200 외 오류, 로딩 실패, 리디렉션 오류 등 비정상 페이지
*   **디자인 필터:** 과도한 3D/WebGL, 풀스크린 스크롤형, 탐색 불가능 구조, 비대칭 레이아웃 과다, Aesop 스타일 반복, 니치 향수 편중
*   **중복 제거 (기존 DB 비교):** `master_references.txt`와 URL, Root Domain, Brand, UX/IA 패턴이 일치하는 경우
*   **동일 사이트 변형 금지:** 동일 브랜드의 서브 도메인, 상세/이벤트 페이지 등 디자인 시스템이 같은 하위 페이지

## 3. 2차 심층 분류 및 평가

수집된 후보 사이트는 아래 기준에 따라 평가하며, **3가지(디자인, 사용성, 결합) 요건을 모두 충족하는 경우에만** 최종 결과로 인정한다.

1.  **[디자인 적합] (4개 이상 충족):** 충분한 여백, 타이포그래피 중심, 스토리 기반 흐름, 제한된 컬러(≤3), 오브제화된 이미지, Oriental Modern 무드
2.  **[사용성 적합] (4개 이상 충족):** Depth 2 이하 네비게이션, 3클릭 이내 제품 접근, 명확한 Grid/리스트, 필터/정렬 존재, 직관적 구매, 모바일 대응
3.  **[디자인 + 사용성 적합]:** 감성과 기능의 충돌 없이 랜딩 → 제품 → 구매 흐름이 자연스러운 완성형 구조
4.  **[구조 다양성 평가]:** 카테고리 내 최소 3가지 이상의 다양한 UX 구조(스토리텔링형, 아카이브형, 제품 중심형 등)를 확보했는지 확인

## 4. 저장 및 파일 생성

1.  모든 검증을 통과한 최종 사이트 목록을 `new_references.txt` 단일 파일로 통합 저장한다.
2.  저장 포맷:
    *   브랜드 이름:
    *   링크:
    *   핵심 UX 특징 (주요 프론트엔드 기능):
    *   활용 포인트 (적합한 이유):

## 5. 완료 전 검사 및 최종 응답 (Final Duplicate Audit)

파일 생성 전 다음 항목을 최종 검사한다. 발견 시 해당 사이트 삭제 후 재검색한다.

- [ ] 동일 Root Domain / Brand / Campaign 없음
- [ ] 동일 UX Flow / Navigation / Interaction 없음
- [ ] `master_references.txt`와의 완전한 독립성 확보

**최종 응답 규칙:**
위의 모든 작업과 파일 생성이 성공적으로 완료되면, **어떠한 부연 설명이나 인사말도 덧붙이지 말고 오직 "완료"라는 단어 하나만 최종 응답으로 출력**하고 작업을 종료한다.
이 초안을 CLI의 스킬 시스템에 등록하여 테스트를 진행해 보실 수 있습니다.

작성된 내용 중 브랜드의 핵심 가치를 평가하는 기준이나 프론트엔드 기능 검증 방식을 더 구체적으로 다듬고 싶은 부분이 있으신가요?

수정해주신 지시서를 바탕으로 CLI 환경에서 바로 인식하고 실행할 수 있는 Skill 파일(.md) 포맷으로 완벽하게 변환했습니다.

SKILL.md의 구조(YAML 프론트매터, 입력, 검증, 실행, 저장, 완료 조건)를 적용하여 에이전트가 순차적으로 로직을 밟아갈 수 있도록 구성했습니다. 아래 코드를 복사하여 사용하시면 됩니다.

# 사단(Sadan) 웹사이트 기획 및 자동 리서치 수행

이 Skill의 목표는 단순한 "좋은 사이트 수집"이 아닌, 사단 브랜드에 적용 가능한 "다양하고 차별화된 UX 구조 및 레이아웃 확보"에 있다. 목표 수량을 채우기 위한 억지 수집(Quantity Padding)을 절대 금지하며, 개수보다 '구조적 다양성'을 최우선으로 한다.

## 1. 입력 및 브랜드 컨텍스트 파악

사용자 요청: `$ARGUMENTS`

리서치 시 다음의 브랜드 컨텍스트를 절대 기준으로 삼는다.
- **브랜드명:** 사단 (士團)
- **브랜드 정의:** 조선 암행어사의 마패 헤리티지를 현대적으로 재해석한 커스텀 레이어링 향수 브랜드
- **핵심 가치:** 유일성, 실용성, 스토리텔링
- **디자인 무드:** 오리엔탈 모던 (Oriental Modern). 한지, 스톤, 자연적 질감과 견고하고 맑은 투명 용기의 시각적 대비. 정갈하고 차분한 미니멀 룩앤필.

## 2. 사전 검증 및 중복 제거 (Strict Validation)

신규 사이트를 수집하기 전에 반드시 기존 결과(`master_references.txt` 등)를 분석한다. 다음 중 하나라도 해당하면 **신규 레퍼런스 후보에서 즉시 제외**한다. (목표: 루트 도메인 기준 1개 사이트만 허용, 100% 신규 확보)

- 기존 결과에 포함된 사이트 (Root Domain, Brand Name 동일 시)
- 동일 사이트의 다른 하위 페이지 또는 서브 도메인
- 동일 브랜드의 국가별 사이트, 캠페인, 랜딩, 이벤트 페이지
- 동일 디자인 시스템 기반 템플릿

## 3. 수집 및 필터링 규칙

1. **링크 유효성 검증:** HTTP 상태 코드 200 필수. 로딩 실패, 리디렉션 오류, dead link, 렌더링 실패 시 수집 금지.
2. **디자인 배제 대상:**
   - 과도한 3D 및 WebGL 사용 사이트
   - 정보 탐색을 방해하는 원페이지 풀스크린 스크롤형 사이트
   - 비대칭 레이아웃이 과다하여 가독성을 해치는 사이트
   - 이솝(Aesop) 스타일의 단순 반복 복제 사이트
   - 특정 니치 향수(Niche Perfume) 브랜드에만 편중된 사이트
3. **UX 구조 중복 금지:**
   - Navigation depth, 콘텐츠 흐름, 레이아웃 Grid 구조, CTA 위치, 인터랙션 방식 중 **2개 이상 일치 시 동일 구조로 판단하여 제외**한다.
4. **카테고리 다양성 확보:** 하나의 카테고리 내에서 최소 3가지 이상의 서로 다른 UX 구조를 확보한다.
   - *Editorial 예시:* 스토리텔링 스크롤형, 챕터 분할형, 비주얼 아카이브형, 좌우 50:50 Split-screen형 등
   - *Commerce 예시:* 제품 포커스형, 라이프스타일 룩북 결합형, 가로 스와이프(Horizontal) 탐색형, Sticky 사이드바 필터형 등

## 4. 리서치 결과 평가 및 분류

수집된 각 사이트를 아래 3가지 기준으로 철저히 평가한다. **아래 3가지 기준을 완벽하게 모두(100%) 충족하는 결과만 최종 출력 대상이 된다.**

- **[1. 디자인 적합]:** 충분한 여백, 낮은 정보 밀도, 타이포그래피 중심, 제한된 컬러(3개 이하) 사용, 오리엔탈 모던 무드 일치.
- **[2. 사용성 적합]:** Depth 2 이하 네비게이션, 명확한 Grid/리스트 구조, 직관적 필터 및 구매 흐름, 모바일 대응.
- **[3. 디자인+사용성 완벽 적합]:** 위 1번과 2번 조건을 모두 충족하며, 감성과 기능이 충돌 없이 랜딩에서 구매까지 자연스럽게 이어지는 완성형 사이트.

## 5. 결과 작성 및 파일 저장

1. 평가를 최종 통과한 사이트들은 단일 통합 파일인 `new_references.txt`에 저장한다.
2. 기존 데이터와 UX 패턴, 도메인 등이 겹칠 경우 절대 저장하지 않는다.
3. 파일에 기록할 출력 포맷은 다음과 같다:
   - 브랜드 이름: 
   - 링크: (URL)
   - 주요 프론트엔드 기능: (예: Hover 시 텍스처 이미지 스왑, Sticky 스크롤 등)
   - 적합한 이유: (사단 브랜드의 컨텍스트 및 와이어프레임 기준과 어떻게 부합하는지 1~2줄 작성)

## 6. 완료 전 검사 (Final Duplicate Audit)

파일 생성 직전, 다음 항목을 최종 검사하여 **하나라도 중복 및 실패 조건 발견 시 즉시 해당 사이트 삭제 후 재검색**한다.
- [ ] 동일 구조(UX 흐름/탐색 경험) 사이트가 반복되지 않았는가?
- [ ] 접속 불가 링크가 완전히 배제되었는가?
- [ ] 중복 도메인이나 동일 브랜드가 없는가?
- [ ] 특정 카테고리에 편중되지 않고 구조적 다양성이 확보되었는가?

## 7. 최종 응답 규칙

위의 모든 리서치, 검증 및 `new_references.txt` 파일 생성 작업이 성공적으로 완료되면, 에이전트는 어떠한 부연 설명이나 인사말도 덧붙이지 말고 **오직 "완료"라는 단어 하나만 최종 응답으로 출력**하고 작업을 종료한다.

# 데이터 분류 수행

이 Skill은 승인된 원본 데이터를 정해진 기준에 맞게 분류하고 구조화하는 역할만 수행한다. 새로운 데이터를 스스로 창작하거나, 기준에 없는 임의의 카테고리를 생성하지 않는다.

## 승인 게이트

1. `${CLAUDE_PROJECT_DIR}/CLAUDE.md`와 `output/workflow-status.md`를 읽는다.
2. 이전 단계(예: 데이터 수집)가 `approved`인지 확인한다.
3. `input/taxonomy.md` (분류 기준서)가 존재하는지 확인하고 기준을 숙지한다.
4. 기준 파일이나 원본 데이터가 없으면 사용자에게 무엇이 필요한지 알리고 중단한다.

## 입력

사용자 요청: `$ARGUMENTS`

- 인수가 비어 있으면 기본 원본 데이터 경로(`output/01_collection/raw-data.md`)를 사용한다.
- 입력된 원본 데이터의 전체 개수와 각각의 고유 식별자(ID) 또는 출처를 파악한다.

## 분류 절차

# 데이터 분석 수행

이 Skill은 구조화(분류)된 데이터를 기반으로 논리적이고 객관적인 인사이트를 도출한다. 데이터에 없는 사실을 지어내거나(환각), 논리적 비약(과도한 추측)을 범하지 않는다. 결과를 스스로 승인하지 않는다.

## 승인 게이트

1. `${CLAUDE_PROJECT_DIR}/CLAUDE.md`와 `output/workflow-status.md`를 읽는다.
2. 이전 단계(예: 데이터 분류)의 상태가 `approved`인지 확인한다.
3. `output/02_classification/classification-result.md` 파일이 존재하는지 확인한다.
4. 승인 상태가 아니거나 파일이 없으면 무엇이 필요한지 알리고 중단한다.

## 입력

사용자 요청: `$ARGUMENTS`

- 인수가 비어 있으면 `output/02_classification/classification-result.md`를 기본 데이터로 사용한다.
- `input/topic.md` 또는 `input/client-brief.md`가 있다면 읽고, 분석의 궁극적인 목적과 타겟을 확인한다.

## 분석 절차

1. **패턴 및 상관관계 파악:** 분류된 데이터 카테고리 간의 공통점, 차이점, 반복되는 키워드나 신호를 찾는다.
2. **핵심 인사이트 도출(So What?):** 단순한 사실의 나열을 넘어, "이 데이터가 프로젝트/비즈니스에 어떤 의미를 갖는가?"를 3~5가지의 핵심 메시지로 정리한다.
3. **사실과 해석 분리:** 분석 내용 작성 시 원본 데이터에 명시된 '사실(Fact)'과 에이전트가 도출한 '해석(Interpretation)'을 명확히 구분하여 서술한다.
4. **특이점 및 한계 명시:** 쏠림 현상이 있거나 미분류된 데이터가 있다면, 이것이 갖는 의미나 분석의 한계점을 반드시 짚고 넘어간다.

## 작성

1. `templates/analysis-template.md`의 필수 구조를 사용한다. (템플릿이 없을 경우 '핵심 요약 → 상세 분석 → 결론 및 시사점' 순으로 작성)
2. 각 인사이트에는 반드시 분류 결과 문서의 어떤 항목에서 도출되었는지 명확한 근거(예: `[분류 카테고리명]` 또는 `[출처 번호]`)를 연결한다.
3. 변화나 비교가 중요한 경우 마크다운 표를 활용하여 시각적으로 정리한다.
